# Taste
- Prefers test automation framework tooling installed as devDependencies via `npm install -D` (e.g., dotenv, csv-parse, xlsx, winston, faker, jsonpath, ajv, allure). Confidence: 0.8
- Prefers Playwright test runs to always record video and traces, and capture screenshots on failures (video: 'on', trace: 'on', screenshot: 'only-on-failure'). Confidence: 0.9
- Prefers a custom HTML reporter registered in the Playwright config and the generated HTML report to auto-open in Chrome (or default browser) after each run — explicitly requested "open my custom report in chrome after each run". Confidence: 0.95
- Prefers comprehensive, self-contained README/docs that let anyone use the project without prior knowledge — covering framework details, setup, configuration, usage, and troubleshooting. Confidence: 0.8
- Runs the project on Windows (PowerShell) with Playwright — commands and paths must work with Windows shell semantics. Confidence: 0.9
- When troubleshooting, prefers the assistant to reproduce the exact failure with the exact command they ran before diagnosing, and to give the root cause plus a copy-pasteable fix in a comparison table. Confidence: 0.8
- Prefers documentation that is visually attractive and easy to scan — emojis, badges, tables, diagrams (e.g., Mermaid), and annotated code blocks. Confidence: 0.8
- Prefers to confirm feasibility and get explicit approval before applying changes (e.g., "first let me know, once approved then only start"; "inform me, don't make any changes until I say"). Confidence: 0.95
- Prefers minimal-scope changes — only modify exactly what was requested and touch nothing else unless asked (e.g., when deleting reports, "don't delete anything else except report files"). Confidence: 0.95
- When rebranding text (headings, branding), prefers updating all occurrences for consistency — main heading, subheading, browser tab title, and history page — rather than only the most visible spots. Confidence: 0.7
- After changing code that affects generated output (e.g., report branding), expects the change to be verified end-to-end — re-run the relevant test, confirm the new text appears in the regenerated artifact, and view it in the browser. Confidence: 0.9
- Prefers identity/branding metadata (e.g., test author name shown in the report) to be fixed at its central source (e.g., `.env` env var read by the reporter) so the corrected value applies to all upcoming test runs, not just one test. Confidence: 0.8
- When asked for completion status, wants a direct, affirmative answer ("Yes") backed by actual verification that the work is done and all files are saved on disk (e.g., git status/grep), not just an assumption. Confidence: 0.7
- Prefers completed work to be committed and pushed to GitHub after implementation, not just saved locally. Confidence: 0.7
- Prefers generated artifacts (custom HTML reports, run snapshots, logs) to be gitignored so only source code, configs, and docs are committed to the repo. Confidence: 0.7
- Prefers stale test-run artifacts (custom reporter HTML reports, playwright-report, test-results, flaky run snapshots, logger output) to be deleted from the workspace when no longer needed, rather than left to accumulate — keeping the working tree clean so the next run regenerates everything fresh. Confidence: 0.7
- Keeps the README/docs in sync with the actual project state — when branding or configuration changes (e.g., report name, author), the README should be updated to match. Confidence: 0.7
- Prefers behavior-affecting additions to be gated behind an environment-variable toggle (e.g., `OPEN_REPORT=false` to disable auto-opening the report) so the feature can be turned off without code changes. Confidence: 0.8
- Wants to be shown how to enable/disable feature toggles themselves for later use — both the permanent `.env` setting and the one-run command-line override — so they can control behavior without asking each time. Confidence: 0.8
- When a delivered feature doesn't work in their hands (e.g., report didn't auto-open), expects the assistant to reproduce the failure, diagnose the actual root cause, fix it, and re-verify — not just re-explain the configuration. Confidence: 0.8
- When reporting a problem (e.g., "why is my report showing 0 tests?"), wants the issue fixed AND the root cause explained explicitly ("fix the issue and tell me what was the problem") — diagnosis is part of the deliverable, not optional context. Confidence: 0.8
- Cares that test runs behave correctly in CI (Jenkins/GitHub Actions), not just locally — when a misconfigured/empty run would silently produce a misleading "0 tests, all pass" report, prefers it to fail loudly with a non-zero exit so CI surfaces the real problem. Confidence: 0.6
- When a reported issue turns out to be user error rather than a code bug, wants the project restored to its exact pre-issue state — expects the assistant to audit the whole project (not just files it remembers touching) and revert only changes made during the troubleshooting session, while preserving the user's pre-existing uncommitted work. Confidence: 0.85
- When instructions are ambiguous or data is missing (e.g., during a revert/restore task), prefers the assistant to ask for clarification before proceeding rather than guess. Confidence: 0.7
- Answers direct yes/no confirmation questions with the concise verdict first ("just confirm with yes or no") before elaborating with details or rationale. Confidence: 0.7
